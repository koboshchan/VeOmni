These four configs train Lumine with Qwen/Qwen3-VL-2B-Instruct and the native
`qwen3vl` ChatML template. Stage 0 injects text-only knowledge, stage 1 learns
image-to-action pairs, stage 2 adds instructions, and stage 3 conditions actions
on a supplied thought. The reasoning preprocessor puts that thought in the user
turn. It does not wrap it in think tags or supervise hidden reasoning.

Use this fork's updated runtime, not an unmodified upstream installation.
`model.add_custom_tokens: true` keeps the action-token vocabulary enabled in
every stage, including knowledge injection, so later exports retain it. Only seven
entries are new to Qwen: `<|action_start|>`, `<|action_end|>`, `<|use_abs|>`,
`<|thought_start|>`, `<|thought_end|>`, `Eleven`, and `Twelve`, in that order.
Existing key words stay in the base vocabulary; action whitespace, ordinary
leading-space BPE, and numeric mouse coordinates are unchanged. This registry
cleanup does not migrate or relabel trained token IDs.
`model.chat_template`, `model.optimizer`, `model.accelerator`,
`data.dataloader`, `train.checkpoint`, and `train.wandb` use the nested
upstream argument schema. The old `rmpad`, `data.chat_template`, and flat
training optimizer/checkpoint fields are not valid replacements.

Launch from the Lumine repository, with the updated VeOmni checkout importable.
For sibling checkouts in `~/repos`, after activating a GPU training environment
installed for VeOmni, run the following commands in sequence. These are launch
examples, not commands run during the config validation.

```bash
cd ~/repos/Lumine
export VEOMNI_DIR="$(realpath ../VeOmni)"
export PYTHONPATH="$VEOMNI_DIR${PYTHONPATH:+:$PYTHONPATH}"
export TOKENIZERS_PARALLELISM=false

torchrun --standalone --nproc-per-node=1 "$VEOMNI_DIR/tasks/train_vlm.py" \
  "$VEOMNI_DIR/configs/multimodal/qwen3_vl/lumine_stage0_knowledge.yaml"
torchrun --standalone --nproc-per-node=1 "$VEOMNI_DIR/tasks/train_vlm.py" \
  "$VEOMNI_DIR/configs/multimodal/qwen3_vl/lumine_stage1_pretrain.yaml"
torchrun --standalone --nproc-per-node=1 "$VEOMNI_DIR/tasks/train_vlm.py" \
  "$VEOMNI_DIR/configs/multimodal/qwen3_vl/lumine_stage2_instruct.yaml"
torchrun --standalone --nproc-per-node=1 "$VEOMNI_DIR/tasks/train_vlm.py" \
  "$VEOMNI_DIR/configs/multimodal/qwen3_vl/lumine_stage3_reasoning.yaml"
```

Each config reads `configs/data_knowledge.yaml`, `configs/data_pretrain.yaml`,
`configs/data_instruct.yaml`, or `configs/data_reasoning.yaml` relative to the
Lumine working directory. Their source names must remain `lumine_knowledge`,
`lumine_pretrain`, `lumine_instruct`, and `lumine_reasoning`; those names
select the registered preprocessors. Dataset source paths and frame paths must
also resolve from that working directory. Prepare the JSONL files before
launching. In particular, the instruction config's `genshin_actions.jsonl` and
the reasoning config's `lumine_reasoning` source are not generated by training.
Multimodal records need an `images` array of frame paths, not just the recorder's
raw `image` field.

Stage 0 starts from the public model. Every later stage loads its predecessor's
`output/lumine_stageN_NAME_qwen3vl_2b/hf_ckpt/latest` alias as an HF model.
The runtime's opt-in `train.checkpoint.update_latest: true` publishes that
alias after a successful HF export. The real upstream export directory is
`output/lumine_stageN_NAME_qwen3vl_2b/checkpoints/global_step_N/hf_ckpt`;
the alias points there, not to a DCP weights directory. HF weights and their
tokenizer/processor sidecars must be present before starting the next stage.
Both DCP and HF export are enabled at epoch boundaries, and HF export is also
enabled at training end. To resume a stage's optimizer, scheduler, and data
cursor, use `--train.checkpoint.load_path auto` for that same output directory.
Loading the previous stage's HF model starts a new stage with a fresh optimizer.

These are starting configs, not measured GPU presets. They use FSDP2,
FlashAttention 2, non-reentrant gradient checkpointing, one sequence-parallel
rank, and packed dynamic batches. Knowledge uses a 4096-token context; the other
stages use 8192. ViT is frozen for knowledge and reasoning and trained for
pretraining and instruction tuning. WandB is off unless enabled explicitly.
The global batches are 8, 8, 8, and 4, with microbatch 1; the data-parallel world
size must divide the global batch. Increase GPU count or reduce context/image
budgets if memory requires it.

Under the current upstream dynamic-batching API, `data.train_size` is a
packed-token budget per epoch, not a number of examples. The starting budgets
are 8 million, 80 million, 32 million, and 8 million tokens respectively. Set
them from the prepared corpus before a full run. The old sample-count comments
and `train_size: -1` knowledge setting must not be copied into this API.
No debug `max_steps` cap is included. These budgets, contexts, and learning
rates do not reproduce the old 7B Blackwell presets.

The configs can be checked on CPU by parsing them with
`VeOmniVLMArguments` and calling `compute_train_steps()`. That validates the
nested fields and batching arithmetic without loading model weights or
starting distributed training. A GPU training smoke test is still required
before treating them as a validated training recipe.

OBS frames are 1280x720 at 30 FPS, with absolute actions already in that
coordinate system. All four configs set image_min_pixels and image_max_pixels
to 921600 and require image_frame_width=1280/image_frame_height=720.
The image pipeline preserves those pixels exactly, then pads 16 black rows
at the bottom to meet Qwen3-VL's 32-pixel merged patch grid (1280x736).
HF resizing is disabled for this mode, so there is no stretching, cropping,
or coordinate rescaling. Unexpected frame dimensions fail explicitly.
30 FPS describes recording cadence, not the optional video sampler's fps.
